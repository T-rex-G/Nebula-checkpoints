# Nebulaverse-X Phase 1 Task 2 — Optional GitHub App Foundation

## Status
Approved for implementation on 2026-07-21. This design preserves PAT, GitHub OAuth, GitLab, and Gitea authentication. GitHub App authentication remains optional and disabled when it has no configuration.

## Objective
Add a server-owned GitHub App connection path that uses short-lived installation tokens without exposing the App private key, client secret, temporary user token, or installation token to browser JavaScript.

## Architecture

### Configuration
`src/config.js` exposes `loadGithubAppConfig(env, options)`. An entirely absent configuration returns `{ enabled: false }`. A partially configured deployment fails closed with a clear configuration error. Production callback URLs must use HTTPS. The required values are App ID, app slug, client ID, client secret, private key, and callback URL (or `PUBLIC_BASE_URL` from which the callback is derived). The webhook secret is parsed and reported as configured but is not exposed.

### User authorization and installation claim
A signed-in GitHub PAT or OAuth identity initiates the flow through a CSRF-protected POST. Nebulaverse-X first performs the GitHub App user authorization flow. The callback state is HMAC-signed, expires after ten minutes, is bound to the encrypted session nonce and active identity, and is consumed once. The returned GitHub App user token is retained only in the sealed server session for the installation-claim window.

Nebulaverse-X then redirects to the GitHub App installation URL with a second signed state. The setup callback rejects spoofed installation IDs by requiring the temporary GitHub App user token to list the claimed installation through `GET /user/installations`. The server also verifies the installation with an App JWT through `GET /app/installations/{installation_id}` and rejects mismatched or suspended installations.

### Credential broker
`src/github-app.js` creates RS256 App JWTs and brokers installation tokens. Installation tokens are cached only until sixty seconds before GitHub's expiry and coalesced across concurrent requests. Cache keys contain only App ID and installation ID. The broker revalidates installation ownership and suspension before minting a token and removes cached material on disconnect or authorization failure.

`src/provider-credentials.js` is the single credential-resolution boundary. PAT, OAuth, GitLab, and Gitea accounts pass through their existing token. GitHub App accounts receive an ephemeral clone containing the current installation token; the session account never contains that token.

### Session account model
A GitHub App connection is stored as a tokenless account with `authMethod: "github-app"`, `installationId`, installation account metadata, repository selection, granted permissions, the authorizing GitHub login/id, and a stable authorizing identity key. Existing PAT or OAuth accounts for the same login are retained.

### Persistence and audit
Migration `006_github_app.sql` stores non-secret installation metadata and non-secret lifecycle audit events when Neon is enabled. Without Neon, the connection remains available in the sealed cookie session and lifecycle events are emitted as structured non-secret logs. Events include connected, disconnected, authorization refreshed, suspended, and rejected.

### API and UI
- `POST /api/github-app/connect`: returns the GitHub authorization URL.
- `GET /api/github-app/oauth/callback`: validates and consumes user-authorization state, exchanges the code, verifies the user, and redirects to installation.
- `GET /api/github-app/setup`: validates and consumes installation state, verifies ownership, registers the installation, and redirects home.
- `GET /api/github-app/status`: returns only non-secret configuration and connection metadata.
- `POST /api/github-app/refresh`: revalidates installation health and metadata.
- `POST /api/github-app/disconnect`: removes local registration and invalidates broker state.

The Settings dialog shows availability, connected installations, scope, health, authorizing user, reauthorize, refresh, and disconnect controls. PAT login and OAuth remain visible and unchanged.

## Failure behavior
All callback tampering, expiry, replay, identity changes, ownership mismatches, missing configuration, revoked installations, and suspended installations fail closed. Provider secrets are never included in JSON responses, URLs generated by Nebulaverse-X, structured logs, audit payloads, or public assets.

## Verification
The implementation requires unit tests for configuration, state signing, JWT signing, credential caching/concurrency, revocation and suspension; server/contract tests for routes, session boundaries, UI, packaging, and non-exposure; the existing complete regression suite; syntax and secret scans; and clean-extraction package verification.
